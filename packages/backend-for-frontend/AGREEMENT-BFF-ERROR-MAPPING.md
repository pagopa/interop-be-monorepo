# BFF errors mapping

> **Not documented**:
> - Authentication: none — no BFF-specific error is raised while authenticating every request. Errors from specific login endpoints remain documentable.
> - Infrastructure: `selfcareEntityNotFilled`, `attributeNotExists`, `dynamoReadingError`, `missingInterface`, `noDescriptorInEservice`, `missingDescriptorInClonedEservice`, `missingSelfcareId`, `privacyNoticeVersionIsNotTheLatest`, `missingActivePurposeVersion`, `activeAgreementByEserviceAndConsumerNotFound`, `purposeIdNotProvided`, `cannotGetKeyWithClient`, `clientAssertionPublicKeyNotFound`, `delegatedEserviceNotExportable`, `missingUserRolesInIdentityToken`, `noVersionInEServiceTemplate`, `delegationContractNotFound`.
> - Unused (no throw site in the BFF): `eserviceIsNotDraft`, `invalidJwtClaim`, `eserviceTemplateIsNotPublished`, `tooManyDescriptorForInterfaceWithTemplate`, `eserviceTemplateInterfaceNotFound`, `invalidInterfaceFile`, `eserviceTemplateInterfaceDataNotValid`, `invalidEserviceInterfaceFileDetected`, `operationForbidden`.
>
> Routers covered: `agreementRouter`.

## `agreementDescriptorNotFound`

The descriptor of the agreement was not found in the e-service.

| Router | BFF endpoint | When it happens | Reachable from the FE? | Steps to reproduce (UI) | Resolution steps |
| ------ | ------------ | --------------- | ---------------------- | ----------------------- | ---------------- |
| `agreementRouter` | `POST /agreements/:agreementId/approve` | `approveAgreement` calls `enrichAgreement`, which calls `getCurrentDescriptor`; it throws when the descriptor ID on the agreement returned by agreement-process is absent from the e-service returned by catalog-process. `approveAgreementErrorMapper` exposes this as 404. | **CAN HAPPEN (UNVERIFIED)** — A provider admin can activate a pending request. This error requires catalog-process to lose or omit the agreement descriptor after the details page has loaded; verify whether a normal descriptor lifecycle change can cause that timing window while a request is pending. | **Data precondition:** Tenant A has an admin user and a pending agreement from tenant B. Its descriptor is present when the page loads, but the catalog-process e-service response used after approval omits that descriptor. <br> 1. Sign in as tenant A’s admin and open `/erogazione/richieste` (“Richieste di fruizione ricevute”). <br> 2. Open the pending agreement to load `/erogazione/richieste/{agreementId}`. <br> 3. While the page remains open, cause the catalog response for that e-service to omit the agreement’s descriptor. **Unverified:** confirm that a normal UI descriptor lifecycle action can produce this state while the request is pending. <br> 4. Click “Attiva” and confirm the action. | 🔴 **Impossible resolution** — Tenant A cannot repair the catalog/agreement data mismatch from the agreement page. Support or a backend correction must restore a matching descriptor. |
| `agreementRouter` | `POST /agreements/:agreementId/unsuspend` | `unsuspendAgreement` calls `enrichAgreement`, which calls `getCurrentDescriptor`; it throws when the descriptor ID on the agreement returned by agreement-process is absent from the e-service returned by catalog-process. `unsuspendAgreementErrorMapper` exposes this as 404. | **CAN HAPPEN (UNVERIFIED)** — An admin can reactivate an agreement suspended by their tenant. This error requires catalog-process to lose or omit the agreement descriptor after the details page has loaded; verify whether a normal descriptor lifecycle change can cause that timing window while an agreement is suspended. | **Data precondition:** Tenant A has an admin user and a suspended agreement for which A is the consumer and initiated the suspension. Its descriptor is present when the page loads, but the catalog-process e-service response used after reactivation omits that descriptor. <br> 1. Sign in as tenant A’s admin and open `/fruizione/richieste` (“Richieste di fruizione inoltrate”). <br> 2. Open the suspended agreement to load `/fruizione/richieste/{agreementId}`. <br> 3. While the page remains open, cause the catalog response for that e-service to omit the agreement’s descriptor. **Unverified:** confirm that a normal UI descriptor lifecycle action can produce this state while the agreement is suspended. <br> 4. Click “Attiva” and confirm the action. | 🔴 **Impossible resolution** — Tenant A cannot repair the catalog/agreement data mismatch from the agreement page. Support or a backend correction must restore a matching descriptor. |

## `contractNotFound`

The contract was not found for the agreement.

| Router | BFF endpoint | When it happens | Reachable from the FE? | Steps to reproduce (UI) | Resolution steps |
| ------ | ------------ | --------------- | ---------------------- | ----------------------- | ---------------- |
| `agreementRouter` | `GET /agreements/:agreementId/contract` | `getAgreementContract` throws `contractNotFound` when agreement-process returns an agreement without a contract and its state is not `ACTIVE`, `SUSPENDED`, or `ARCHIVED`. | Cannot happen — there is no generated operation or UI usage for this endpoint. The frontend has an unreferenced `downloadContract` helper, but its rendered download control calls only `/signedContract`. | — | — |
| `agreementRouter` | `GET /agreements/:agreementId/signedContract` | `getAgreementSignedContract` throws `contractNotFound` when agreement-process returns an agreement without a signed contract and its state is not `ACTIVE`, `SUSPENDED`, or `ARCHIVED`. | **CAN HAPPEN (UNVERIFIED)** — The provider details component renders “Scarica richiesta di fruizione” whenever `isContractPresent` is true and does not disable it when `isDocumentReady` is false. Whether a non-active agreement can have a contract but no signed contract needs verification. | **Data precondition:** Tenant A has an admin user and a pending agreement whose contract is present but whose signed contract is absent. **Unverified:** confirm that the agreement process can return this combination for a pending agreement. <br> 1. Sign in as tenant A’s admin and open `/erogazione/richieste` (“Richieste di fruizione ricevute”). <br> 2. Open the pending agreement to load `/erogazione/richieste/{agreementId}`. <br> 3. In “Informazioni generali”, click “Scarica richiesta di fruizione”. | 🔴 **Impossible resolution** — The agreement details show that a contract exists, but the signed document is missing. Support or a backend correction is needed to generate or restore the document. |

## `contractException`

There is no contract available to download for the agreement.

| Router | BFF endpoint | When it happens | Reachable from the FE? | Steps to reproduce (UI) | Resolution steps |
| ------ | ------------ | --------------- | ---------------------- | ----------------------- | ---------------- |
| `agreementRouter` | `GET /agreements/:agreementId/contract` | `getAgreementContract` throws `contractException` when agreement-process returns an agreement without a contract and its state is `ACTIVE`, `SUSPENDED`, or `ARCHIVED`. | Cannot happen — there is no generated operation or UI usage for this endpoint. The frontend has an unreferenced `downloadContract` helper, but its rendered download control calls only `/signedContract`. | — | — |
| `agreementRouter` | `GET /agreements/:agreementId/signedContract` | `getAgreementSignedContract` throws `contractException` when agreement-process returns an agreement without a signed contract and its state is `ACTIVE`, `SUSPENDED`, or `ARCHIVED`. | **CAN HAPPEN** — On the provider details page the download action is rendered when `isContractPresent` is true, without checking `isDocumentReady`; a provider can click it while the signed document is not yet available. The consumer page disables its action while `isDocumentReady` is false. | **Data precondition:** Tenant A has an admin user and an active agreement whose contract is present but whose signed contract is not yet available. <br> 1. Sign in as tenant A’s admin and open `/erogazione/richieste` (“Richieste di fruizione ricevute”). <br> 2. Open the active agreement to load `/erogazione/richieste/{agreementId}`. <br> 3. In “Informazioni generali”, click “Scarica richiesta di fruizione” while the signed document is still unavailable. | 🟢 **Easy resolution** — Wait for signed-document generation to complete, reload the agreement details page, and click “Scarica richiesta di fruizione” again. If the document remains unavailable, contact support. |
