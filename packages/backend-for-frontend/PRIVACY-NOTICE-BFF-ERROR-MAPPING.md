## `privacyNoticeNotFoundInConfiguration`

The privacy notice for the requested consent type was not found in the configuration.

| Router | BFF endpoint | When it happens | Reachable from the FE? | Steps to reproduce (UI) | Resolution steps |
| ------ | ------------ | --------------- | ---------------------- | ----------------------- | ---------------- |
| `privacyNoticeRouter` | `GET /user/consent/:consentType` | `getPrivacyNotice` calls `retrievePrivacyNoticeId`; `consentTypeMap` has no configured ID for the requested consent type. | **CAN HAPPEN** — `RoutesWrapper` mounts `TOSGuard` on authenticated non-public routes, and `useTOSAgreement` automatically requests the user's TOS and privacy-policy consents. A missing configured entry makes that request fail. | **Data precondition:** Tenant A has an Admin user. The BFF's `consentTypeMap` is missing the entry for `TOS` or `PP`. <br> 1. Sign in to Interoperabilità as the Admin user in tenant A. <br> 2. Open the protected route `/erogazione/e-service/crea/` (the `PROVIDE_ESERVICE_CREATE` route). The `TOSGuard` automatically requests both consents; the request for the missing configured consent triggers the error. | 🔴 **Impossible resolution** — a user cannot add a consent mapping in the UI. Restore the missing `consentTypeMap` entry in the BFF configuration and redeploy or restart the BFF as required. |
| `privacyNoticeRouter` | `POST /user/consent/:consentType` | `acceptPrivacyNotice` calls `retrievePrivacyNoticeId`; `consentTypeMap` has no configured ID for the requested consent type. | Cannot happen — `useTOSAgreement` must successfully load both consent queries before `TOSGuard` renders `TOSAgreement`; if this mapping is missing, the corresponding GET fails and the `Accedi` action is not rendered. | — | — |

## `privacyNoticeNotFound`

No current privacy notice version was found in storage for the requested consent type.

| Router | BFF endpoint | When it happens | Reachable from the FE? | Steps to reproduce (UI) | Resolution steps |
| ------ | ------------ | --------------- | ---------------------- | ----------------------- | ---------------- |
| `privacyNoticeRouter` | `GET /user/consent/:consentType` | `getPrivacyNotice` calls `retrieveLatestPrivacyNoticeVersion`; `privacyNoticeStorage.getLatestVersion` returns no record for the configured privacy notice ID. | **CAN HAPPEN** — the authenticated app's `TOSGuard` automatically requests both consent records, so an absent latest-version record is returned as an error before the protected page renders. | **Data precondition:** Tenant A has an Admin user; the BFF has a configured ID for `TOS` or `PP`, but the corresponding latest privacy-notice record is absent from storage. <br> 1. Sign in to Interoperabilità as the Admin user in tenant A. <br> 2. Open the protected route `/erogazione/e-service/crea/` (the `PROVIDE_ESERVICE_CREATE` route). `TOSGuard` requests both consents automatically; the request for the consent type with no latest record triggers the error. | 🔴 **Impossible resolution** — no user-facing action can recreate the latest notice record. Ask the operator or support team to restore the correct privacy-notice data in storage. |
| `privacyNoticeRouter` | `POST /user/consent/:consentType` | `acceptPrivacyNotice` calls `retrieveLatestPrivacyNoticeVersion`; the latest record that existed when `getPrivacyNotice` ran is removed before the user submits consent, so the storage lookup returns no record. | **CAN HAPPEN** — the dialog uses the consent state loaded earlier and does not refetch it before the user clicks `Accedi`; a notice record removed while the dialog is open leaves the displayed action stale. | **Data precondition:** Tenant A has an Admin user who has not accepted the current `TOS` or `PP`; the configured latest notice exists when the consent queries complete. An operator removes that latest notice record while the acceptance dialog is open. <br> 1. Sign in to Interoperabilità as the Admin user in tenant A. <br> 2. Open the protected route `/erogazione/e-service/crea/` and wait for `TOSGuard` to show the consent dialog. <br> 3. While the dialog remains open, have the operator remove the current latest notice record for a consent the user has not accepted. <br> 4. Click `Accedi`. The request uses the previously loaded consent state, while the BFF now finds no latest notice; this is the defect step. | 🔴 **Impossible resolution** — the user cannot restore the notice record. Ask the operator or support team to restore the current notice in storage, then reload and try again. |
