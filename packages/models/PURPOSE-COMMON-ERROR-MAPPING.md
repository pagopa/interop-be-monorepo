# Common errors mapping

> **Not documented** (same for every endpoint, or never surfaced over HTTP):
> - Authentication: `jwtDecodingError`, `invalidClaim`, `missingHeader`, `tokenVerificationFailed`, `badBearerToken`, `badDPoPToken`.
> - Middleware-only: `tooManyRequestsError`.
> - Infrastructure: `authenticationSaslFailed`, `htmlTemplateInterpolationError`, `pdfGenerationError`, `genericError`, `thirdPartyCallError`, `tokenGenerationError`, `missingRSAKey`, `missingKafkaMessageData`, `kafkaMessageProcessError`, `jwksSigningKeyError`, `kafkaApplicationAuditingFailed`, `fallbackApplicationAuditingFailed`, `invalidSqsMessage`, `decodeSQSMessageError`, `pollingMaxRetriesExceeded`.
>
> Processes covered: `purpose-process`.

| ------- | ------------ | --------------- | ---------------------- | ----------------------- | ---------------- |

As tenant A's admin, open `/fruizione/finalita/P/modifica`.<br>2. Open _Assegnazione_.<br>3. Select _Compilazione in autonomia e approvazione del valutatore_ and select a reviewer.<br>4. Click _Salva bozza e prosegui_. | 🔴 **Impossible resolution**<br>1. Ask an operator to set `featureFlagNewOperators=true` in purpose-process configuration.<br>2. Retry the assignment. |
| `purpose-process` | `POST /purposes/:purposeId/riskAnalysis/submit` | `submitRiskAnalysis` calls `assertFeatureFlagEnabled(config, "featureFlagNewOperators")` before retrieving the purpose. | **CAN HAPPEN** — the admin editor renders the approval-request action from the purpose's stored review mode; the FE has no flag check. | **Data precondition:** `featureFlagNewOperators=false`; tenant A has a draft purpose P in `ADMIN_WRITES_REVIEWER_SIGNS` mode, created while the feature was enabled or retained after a flag change.<br>1. As tenant A's admin, open `/fruizione/finalita/P/modifica`.<br>2. In _Analisi del rischio_, edit an answer.<br>3. Click _Salva bozza e prosegui_, then click _Conferma_ in the approval-request dialog. | 🔴 **Impossible resolution**<br>1. Ask an operator to set `featureFlagNewOperators=true` in purpose-process configuration.<br>2. Retry the approval request. |
| `purpose-process` | `POST /purposes/:purposeId/riskAnalysis/sign` | `signRiskAnalysis` calls `assertFeatureFlagEnabled(config, "featureFlagNewOperators")` before retrieving the purpose. | **CAN HAPPEN** — the reviewer approval route renders actions from the stored workflow state and does not check `featureFlagNewOperators`. | **Data precondition:** `featureFlagNewOperators=false`; purpose P is awaiting reviewer approval and is assigned to reviewer R, with the workflow created while the flag was enabled or retained after a flag change.<br>1. Sign in as reviewer R.<br>2. Open `/analisi-del-rischio/P/approvazione`.<br>3. Click _Approva analisi del rischio_, then _Conferma_. | 🔴 **Impossible resolution**<br>1. Ask an operator to set `featureFlagNewOperators=true` in purpose-process configuration.<br>2. Retry the approval. |
| `purpose-process` | `POST /purposes/:purposeId/riskAnalysis/reject` | `rejectRiskAnalysis` calls `assertFeatureFlagEnabled(config, "featureFlagNewOperators")` after hyperlink validation and before retrieving the purpose. | **CAN HAPPEN** — the reviewer rejection dialog is rendered from the stored workflow state and has no feature-flag check. | **Data precondition:** `featureFlagNewOperators=false`; purpose P is awaiting reviewer approval and is assigned to reviewer R, with the workflow created while the flag was enabled or retained after a flag change.<br>1. Sign in as reviewer R.<br>2. Open `/analisi-del-rischio/P/approvazione`.<br>3. Click _Rifiuta con motivazione_, enter a plain-text reason, and click _Rifiuta_. | 🔴 **Impossible resolution**<br>1. Ask an operator to set `featureFlagNewOperators=true` in purpose-process configuration.<br>2. Retry the rejection. |
| `purpose-process` | `PUT /purposes/:purposeId/riskAnalysis/form` | `editRiskAnalysisForm` calls `assertFeatureFlagEnabled(config, "featureFlagNewOperators")` before retrieving the purpose. | **CAN HAPPEN** — the reviewer compilation route and save control depend on the stored assignment state, not on a FE feature-flag check. | **Data precondition:** `featureFlagNewOperators=false`; purpose P is assigned to reviewer R in `REVIEWER_WRITES_REVIEWER_SIGNS` mode and is awaiting reviewer compilation.<br>1. Sign in as reviewer R.<br>2. Open `/analisi-del-rischio/P/compilazione`.<br>3. Change an answer and click _Salva bozza e prosegui_. | 🔴 **Impossible resolution**<br>1. Ask an operator to set `featureFlagNewOperators=true` in purpose-process configuration.<br>2. Retry the save. |

## `hyperlinkDetectionError`

The text contains a hyperlink, which is not allowed.

| Process | BFF endpoint | When it happens | Reachable from the FE? | Steps to reproduce (UI) | Resolution steps |
| ------- | ------------ | --------------- | ---------------------- | ----------------------- | ---------------- |
| `purpose-process` | `POST /purposes/:purposeId/riskAnalysis/reject` | `rejectRiskAnalysis` calls `validateNoHyperlinksSafe(rejectionReason)`, which throws `hyperlinkDetectionError` when the rejection reason contains an `http://`, `https://`, or `www.` link. | **CAN HAPPEN** — `DialogRejectRiskAnalysis` validates only required/minimum length; the FE does not reject hyperlinks in the reason field. | **Data precondition:** purpose P is submitted for review and assigned to reviewer R.<br>1. Sign in as reviewer R and open `/analisi-del-rischio/P/approvazione`.<br>2. Click _Rifiuta con motivazione_.<br>3. Enter at least 10 characters in _Motivo rifiuto approvazione_, including `https://example.test`.<br>4. Click _Rifiuta_. | 🟢 **Easy resolution**<br>1. Remove the URL from the rejection reason.<br>2. Submit _Rifiuta_ again. |
