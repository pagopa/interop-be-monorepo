# Common errors mapping

> **Not documented** (same for every endpoint, or never surfaced over HTTP):
> - Authentication: `jwtDecodingError`, `invalidClaim`, `missingHeader`, `jwkDecodingError`, `missingRequiredJWKClaim`, `invalidPublicKey`, `notAllowedPrivateKeyException`, `notAllowedCertificateException`, `badBearerToken`, `invalidKeyLength`, `notAnRSAKey`, `tokenVerificationFailed`, `notAllowedMultipleKeysException`, `badDPoPToken`, `keyTypeNotAllowed`, `invalidJWKClaim`
> - Middleware-only: none; the common errors used by generic validation, rate limiting, and upload limits also have explicit throw sites and are documentable.
> - Infrastructure: `authenticationSaslFailed`, `htmlTemplateInterpolationError`, `pdfGenerationError`, `genericError`, `thirdPartyCallError`, `tokenGenerationError`, `missingRSAKey`, `missingKafkaMessageData`, `kafkaMessageProcessError`, `jwksSigningKeyError`, `kafkaApplicationAuditingFailed`, `fallbackApplicationAuditingFailed`, `invalidSqsMessage`, `decodeSQSMessageError`, `pollingMaxRetriesExceeded`
>
> Processes covered: `attribute-registry-process`.

## `unauthorizedError`

Unauthorized.

| Process | BFF endpoint | When it happens | Reachable from the FE? | Steps to reproduce (UI) | Resolution steps |
| ------- | ------------ | --------------- | ---------------------- | ----------------------- | ---------------- |
| `attribute-registry-process` | `GET /attributes` | `validateAuthorization` in the process rejects a requester without `ADMIN_ROLE`, `API_ROLE`, `SUPPORT_ROLE`, `SECURITY_ROLE`, `M2M_ROLE` or `M2M_ADMIN_ROLE`. The BFF maps this to 403 but its handler sends no Problem body. | Cannot happen — the FE callers are `ManageAttributesTab` on the admin/support certifier route and attribute autocomplete in admin/API provider create flows; all these roles are admitted by the process. | — | — |
| `attribute-registry-process` | `GET /attributes/origin/:origin/code/:code` | `validateAuthorization` in the process rejects a requester without `ADMIN_ROLE`, `SUPPORT_ROLE` or `M2M_ROLE`. | Cannot happen — no frontend API service or UI call site invokes the origin/code lookup. | — | — |
| `attribute-registry-process` | `GET /attributes/:attributeId` | `validateAuthorization` in the process rejects a requester without `ADMIN_ROLE`, `API_ROLE`, `SUPPORT_ROLE`, `SECURITY_ROLE`, `M2M_ADMIN_ROLE`, `M2M_ROLE`, `REVIEWER_ROLE` or `VIEWER_ROLE`. | Cannot happen — the FE detail and dialog call sites are on routes for roles admitted by this process endpoint, including the certifier details route guarded to admin/support. | — | — |
| `attribute-registry-process` | `POST /certifiedAttributes` | `validateAuthorization` in the process rejects a requester without `ADMIN_ROLE`, `M2M_ROLE` or `M2M_ADMIN_ROLE`. | Cannot happen — the certifier route allows admin/support, but `ManageAttributesTab` renders the create action and drawer only when `AuthHooks.useJwt()` reports `isAdmin`; M2M roles have no UI action. | — | — |
| `attribute-registry-process` | `POST /certifiedDiscreteAttributes` | When the BFF feature flag is enabled, `validateAuthorization` in the process rejects a requester without `ADMIN_ROLE`, `M2M_ROLE` or `M2M_ADMIN_ROLE`; when the flag is disabled, the BFF fails first with `featureFlagNotEnabled`. | Cannot happen — the certifier create action and drawer are rendered only for admin, and M2M roles have no UI action. | — | — |
| `attribute-registry-process` | `POST /declaredAttributes` | `validateAuthorization` in the process rejects a requester without `ADMIN_ROLE`, `API_ROLE` or `M2M_ADMIN_ROLE`. | Cannot happen — the FE creates declared attributes from the e-service create/edit wizard, whose routes require admin/API; M2M admin has no UI action. | — | — |
| `attribute-registry-process` | `POST /verifiedAttributes` | `validateAuthorization` in the process rejects a requester without `ADMIN_ROLE`, `API_ROLE` or `M2M_ADMIN_ROLE`. | Cannot happen — the FE creates verified attributes from the e-service create/edit wizard, whose routes require admin/API; M2M admin has no UI action. | — | — |

## `featureFlagNotEnabled`

Feature flag not enabled.

| Process | BFF endpoint | When it happens | Reachable from the FE? | Steps to reproduce (UI) | Resolution steps |
| ------- | ------------ | --------------- | ---------------------- | ----------------------- | ---------------- |
| `attribute-registry-process` | `POST /certifiedDiscreteAttributes` | The BFF throws `featureFlagNotEnabled` in `attributeService.createCertifiedDiscreteAttribute` when `assertFeatureFlagEnabled(config, "featureFlagAttributeCertifiedDiscrete")` sees the BFF flag disabled; this check runs before calling the process. | **CAN HAPPEN** — the FE form exposes the discrete kind when its runtime `FEATURE_FLAG_ATTRIBUTE_CERTIFIED_DISCRETE` is true, independently of the BFF flag, so a normal submit reaches the BFF check when the flags differ. | **Data precondition:** you are an admin of certifier tenant A; the FE runtime flag `FEATURE_FLAG_ATTRIBUTE_CERTIFIED_DISCRETE=true` and the BFF flag `FEATURE_FLAG_ATTRIBUTE_CERTIFIED_DISCRETE=false`.<br>1. Go to `/aderente/certificatore` and open _Gestione attributi_.<br>2. Click _Crea nuovo_.<br>3. Select _Attributo certificato con valore da personalizzare_, enter a name and description, then click _Crea attributo_. | 🟡 **Medium resolution**<br>1. If certified-discrete attributes should be available, set the BFF `FEATURE_FLAG_ATTRIBUTE_CERTIFIED_DISCRETE=true` and keep the FE runtime flag enabled.<br>2. Otherwise set the FE runtime flag to `false` so the form no longer offers the discrete kind.<br>3. Restart/redeploy the component whose flag changed and reload the page. |

## `hyperlinkDetectionError`

Hyperlink not allowed.

| Process | BFF endpoint | When it happens | Reachable from the FE? | Steps to reproduce (UI) | Resolution steps |
| ------- | ------------ | --------------- | ---------------------- | ----------------------- | ---------------- |
| `attribute-registry-process` | `POST /certifiedAttributes` | `attributeRegistryService.createCertifiedAttribute` calls `validateAttributeSeedFields`, which invokes `validateNoHyperlinksSafe` on the submitted name, description and generated code; the BFF passes the name and description through unchanged. | **CAN HAPPEN** — the certifier drawer checks required/minimum lengths but does not reject or normalize hyperlinks before submitting. | **Data precondition:** you are an admin of certifier tenant A, and the FE can reach the BFF.<br>1. Go to `/aderente/certificatore` and open _Gestione attributi_.<br>2. Click _Crea nuovo_.<br>3. Enter `https://example.com` in _Nome dell'attributo_ and a valid plain-text description in _Descrizione dell’attributo_.<br>4. Click _Crea attributo_. | 🟢 **Easy resolution**<br>1. Remove the hyperlink from the name, description or both, then submit the attribute again. |
| `attribute-registry-process` | `POST /declaredAttributes` | `attributeRegistryService.createDeclaredAttribute` calls `validateAttributeSeedFields`, which invokes `validateNoHyperlinksSafe` on the submitted name and description before checking the origin or duplicate name. | **CAN HAPPEN** — the declared-attribute drawer checks required/minimum lengths but submits its field values without hyperlink validation or normalization. | **Data precondition:** you are an admin/API user of a producer tenant whose origin is in `producerAllowedOrigins`.<br>1.
