# Common errors mapping

> **Not documented** (same for every endpoint, or never surfaced over HTTP):
> - Authentication: `jwtDecodingError`, `invalidClaim`, `missingHeader`, `jwkDecodingError`, `notAllowedPrivateKeyException`, `missingRequiredJWKClaim`, `invalidPublicKey`, `notAllowedCertificateException`, `jwksSigningKeyError`, `tokenVerificationFailed`, `notAllowedMultipleKeysException`, `badBearerToken`, `invalidKeyLength`, `notAnRSAKey`, `badDPoPToken`, `keyTypeNotAllowed`, `invalidJWKClaim`.
> - Middleware-only: —
> - Infrastructure: `authenticationSaslFailed`, `htmlTemplateInterpolationError`, `pdfGenerationError`, `genericError`, `thirdPartyCallError`, `tokenGenerationError`, `missingRSAKey`, `missingKafkaMessageData`, `kafkaMessageProcessError`, `kafkaApplicationAuditingFailed`, `fallbackApplicationAuditingFailed`, `invalidSqsMessage`, `decodeSQSMessageError`, `pollingMaxRetriesExceeded`.
>
> Processes covered: `tenant-process`.

## `operationForbidden`

Insufficient privileges.

| Process | BFF endpoint | When it happens | Reachable from the FE? | Steps to reproduce (UI) | Resolution steps |
| ------- | ------------ | --------------- | ---------------------- | ----------------------- | ---------------- |
| `tenant-process` | `POST /tenants/:tenantId/mails` | The path tenant ID differs from the authenticated UI tenant's organization ID; `assertRequesterAllowed` in `TenantService.addTenantMail` throws `operationForbidden`. | Cannot happen — `UpdatePartyMailDrawer` sends `jwt.organizationId` as `partyId`, and `TenantServices.updateMail` places that same value in the BFF path. | — | — |
| `tenant-process` | `DELETE /tenants/:tenantId/mails/:mailId` | The path tenant ID differs from the authenticated UI tenant's organization ID; `assertRequesterAllowed` in `TenantService.deleteTenantMailById` throws `operationForbidden`. | Cannot happen — the frontend has no delete-mail service or control; `PartyContactsSection` opens `UpdatePartyMailDrawer`, which only issues the POST endpoint. | — | — |
| `tenant-process` | `POST /tenants/delegatedFeatures/update` | The authenticated tenant has no active certified attribute whose ID equals `DELEGATIONS_ALLOWED_ATTRIBUTE_ID`, and `FEATURE_FLAG_DELEGATION_CONSTRAINT_SKIP` is false; `assertTenantAllowedForDelegation` in `TenantService.updateTenantDelegatedFeatures` throws `operationForbidden`. | **CAN HAPPEN** — `AuthGuard` checks eligibility when entering `/aderente/deleghe`, but the drawer does not re-check before saving. If a certifier revokes the attribute while the admin's page remains open, the stale page can still submit and the process checks the current tenant state. | **Data precondition:** tenant A has an admin user and the active certified attribute configured by `DELEGATIONS_ALLOWED_ATTRIBUTE_ID`; `FEATURE_FLAG_DELEGATION_CONSTRAINT_SKIP=false`. Tenant C is the certifier for that attribute and has assigned it to A.<br>1. As tenant A's admin, open `/aderente/deleghe` and select _Disponibilità_.<br>2. Leave that page open. In a separate session, sign in as a tenant C admin and open `/aderente/certificatore` → _Assegnazione attributi_.<br>3. Find A's delegation-eligibility attribute, choose _Revoca attributo_, select _Confermo di aver compreso le conseguenze della revoca_, and confirm with _Revoca_.<br>4. In a fresh tenant A session, open `/aderente/anagrafica` and wait until the configured attribute is no longer listed; keep the original Delegations page open.<br>5. In A's original session, choose _Modifica_, change either _Delega alla fruizione_ or _Delega all’erogazione_, then choose _Aggiorna_. The save is the defect step: the route guard's earlier eligibility result is not checked again. | 🟡 **Medium resolution**<br>1. Ask tenant C's certifier to assign the active attribute configured by `DELEGATIONS_ALLOWED_ATTRIBUTE_ID` to tenant A again.<br>2. Alternatively, an operator can set `FEATURE_FLAG_DELEGATION_CONSTRAINT_SKIP=true` for `tenant-process` and apply the configuration change. |

## `unauthorizedError`

Unauthorized.

| Process | BFF endpoint | When it happens | Reachable from the FE? | Steps to reproduce (UI) | Resolution steps |
| ------- | ------------ | --------------- | ---------------------- | ----------------------- | ---------------- |
| `tenant-process` | `GET /consumers` | The caller has none of `ADMIN_ROLE`, `API_ROLE`, `SECURITY_ROLE`, `SUPPORT_ROLE`, or `VIEWER_ROLE`; `validateAuthorization` in `TenantRouter`'s `getConsumers` handler throws `unauthorizedError`. | Cannot happen — callers are the `PROVIDE_ESERVICE_LIST` and `PROVIDE_PURPOSE_LIST` routes; their `authLevels` are all accepted by this handler's `validateAuthorization`. | — | — |
| `tenant-process` | `GET /producers` | The caller has none of `ADMIN_ROLE`, `API_ROLE`, `SECURITY_ROLE`, `SUPPORT_ROLE`, `VIEWER_ROLE`, or `REVIEWER_ROLE`; `validateAuthorization` in `TenantRouter`'s `getProducers` handler throws `unauthorizedError`. | Cannot happen — the catalog and consumer-purpose routes that call this endpoint admit only roles included in the handler's `validateAuthorization` list. | — | — |
| `tenant-process` | `GET /tenants` | The caller has none of `ADMIN_ROLE`, `API_ROLE`, `SECURITY_ROLE`, `SUPPORT_ROLE`, `M2M_ROLE`, `M2M_ADMIN_ROLE`, `VIEWER_ROLE`, or `REVIEWER_ROLE`; `validateAuthorization` in `TenantRouter`'s `getTenants` handler throws `unauthorizedError`. | Cannot happen — `CREATE_DELEGATION`, `TENANT_CERTIFIER`, and `ASSISTENCE_PARTY_SELECTION` admit only roles accepted by this handler; the tenant-certifier assignment controls are additionally admin-only. | — | — |
| `tenant-process` | `GET /tenants/:tenantId` | The caller has none of `ADMIN_ROLE`, `API_ROLE`, `M2M_ROLE`, `M2M_ADMIN_ROLE`, `SECURITY_ROLE`, `SUPPORT_ROLE`, `INTERNAL_ROLE`, `VIEWER_ROLE`, or `REVIEWER_ROLE`; `validateAuthorization` in `TenantRouter`'s `getTenantById` handler throws `unauthorizedError`. | Cannot happen — `AuthGuard` checks route `authLevels`, and every frontend UI role (`admin`, `support`, `api`, `security`, `reviewer`, `viewer`) is accepted by `getTenantById`. | — | — |
| `tenant-process` | `POST /tenants/:tenantId/attributes/verified/:attributeId` | The caller is not `ADMIN_ROLE`; `validateAuthorization` in `TenantRouter`'s `updateTenantVerifiedAttribute` handler throws `unauthorizedError`. | Cannot happen — `useProviderAgreementGetVerifiedAttributesActions` returns no actions unless `isAdmin`, so non-admin users cannot submit the update from the agreement page. | — | — |
| `tenant-process` | `POST /tenants/:tenantId/mails` | The caller is not `ADMIN_ROLE`; `validateAuthorization` in `TenantRouter`'s `addTenantMail` handler throws `unauthorizedError`. | Cannot happen — `PartyContactsSection` renders the _Modifica_ action only when `isAdmin`; the drawer's submit also requires `jwt.organizationId`. | — | — |
| `tenant-process` | `DELETE /tenants/:tenantId/mails/:mailId` | The caller is not `ADMIN_ROLE`; `validateAuthorization` in `TenantRouter`'s `deleteTenantMailById` handler throws `unauthorizedError`. | Cannot happen — no frontend service, hook, or control calls this DELETE endpoint; the contact drawer only updates mail with POST. | — | — |
| `tenant-process` | `POST /tenants/delegatedFeatures/update` | The caller is not `ADMIN_ROLE`; `validateAuthorization` in `TenantRouter`'s `updateTenantDelegatedFeatures` handler throws `unauthorizedError`. | Cannot happen — `DELEGATIONS` admits support as well as admin, but `DelegationsAvailabilitySection` renders _Modifica_ only when `isAdmin`. | — | — |
| `tenant-process` | `POST /tenants/:tenantId/attributes/certified` | The caller has neither `ADMIN_ROLE` nor `M2M_ROLE` nor `M2M_ADMIN_ROLE`; `validateAuthorization` in `TenantRouter`'s `addCertifiedAttribute` handler throws `unauthorizedError`. | Cannot happen — `TENANT_CERTIFIER` admits support, but `AssignAttributesTab` hides both the assignment button and drawer unless `isAdmin`. | — | — |
| `tenant-process` | `POST /tenants/:tenantId/attributes/certifiedDiscrete` | The caller has neither `ADMIN_ROLE` nor `M2M_ADMIN_ROLE`; `validateAuthorization` in `TenantRouter`'s `addCertifiedDiscreteAttribute` handler throws `unauthorizedError`. | Cannot happen — `TENANT_CERTIFIER` admits support, but `AssignAttributesTab` hides both the assignment button and drawer unless `isAdmin`. | — | — |
| `tenant-process` | `POST /tenants/attributes/declared` | The caller has neither `ADMIN_ROLE` nor `M2M_ADMIN_ROLE`; `validateAuthorization` in `TenantRouter`'s `addDeclaredAttribute` handler throws `unauthorizedError`. | Cannot happen — `DeclaredAttributesListItem` exposes declare/revoke actions only when `isAdmin`, and `SUBSCRIBE_PURPOSE_CREATE` is admin-only. | — | — |
| `tenant-process` | `POST /tenants/:tenantId/attributes/verified` | The caller has neither `ADMIN_ROLE` nor `M2M_ADMIN_ROLE`; `validateAuthorization` in `TenantRouter`'s `verifyVerifiedAttribute` handler throws `unauthorizedError`. | Cannot happen — `useProviderAgreementGetVerifiedAttributesActions` returns no actions unless `isAdmin`. | — | — |
| `tenant-process` | `DELETE /tenants/:tenantId/attributes/verified/:attributeId` | The caller has neither `ADMIN_ROLE` nor `M2M_ADMIN_ROLE`; `validateAuthorization` in `TenantRouter`'s `revokeVerifiedAttribute` handler throws `unauthorizedError`. | Cannot happen — `useProviderAgreementGetVerifiedAttributesActions` returns no actions unless `isAdmin`. | — | — |
| `tenant-process` | `DELETE /tenants/attributes/declared/:attributeId` | The caller has neither `ADMIN_ROLE` nor `M2M_ADMIN_ROLE`; `validateAuthorization` in `TenantRouter`'s `revokeDeclaredAttribute` handler throws `unauthorizedError`. | Cannot happen — `DeclaredAttributesListItem` renders its revoke action only when `isAdmin`. | — | — |

## `hyperlinkDetectionError`

Hyperlink not allowed.

| Process | BFF endpoint | When it happens | Reachable from the FE? | Steps to reproduce (UI) | Resolution steps |
| ------- | ------------ | --------------- | ---------------------- | ----------------------- | ---------------- |
| `tenant-process` | `POST /tenants/:tenantId/mails` | `validateNoHyperlinksSafe` throws `hyperlinkDetectionError` in `TenantService.addTenantMail` when `mailSeed.description` contains an `http://`, `https://`, or `www.` hyperlink. | **CAN HAPPEN** — `UpdatePartyMailDrawer` validates the email and note length but does not remove or reject hyperlink text; changing the email submits the note unchanged. | **Data precondition:** you are `admin` of tenant A and it has a contact email.<br>1. Go to `/aderente/anagrafica`.<br>2. In _Contatti_, choose _Modifica_.<br>3. Change _Indirizzo email ente (richiesto)_ to a different valid email and set _Note_ to `https://example.com`.<br>4. Choose _Aggiorna_. | 🟢 **Easy resolution**<br>1. Remove the hyperlink from _Note_.<br>2. Submit the contact update again. |

## `eventConflictError`

Request conflicts with an ongoing operation on the same resource. Please retry.

| Process | BFF endpoint | When it happens | Reachable from the FE? | Steps to reproduce (UI) | Resolution steps |
| ------- | ------------ | --------------- | ---------------------- | ----------------------- | ---------------- |
| `tenant-process` | `POST /tenants/:tenantId/attributes/verified/:attributeId` | A concurrent write has already committed the same tenant event-stream version; `eventRepository` throws `eventConflictError` from `TenantService.updateTenantVerifiedAttribute`. | **CAN HAPPEN** — two tenant admins can submit an expiration-date update for the same verified attribute from separate sessions before either write completes. | **Data precondition:** tenant A has two admin sessions and an active, pending, or suspended provider agreement whose verified attribute is already verified by A.<br>1. In both sessions, open `/erogazione/richieste/{agreementId}`.<br>2. For the same attribute, choose _Aggiorna verifica_ and change its expiration date.<br>3. Choose _Verifica attributo_ in both sessions before either request completes. | 🟢 **Easy resolution**<br>1. Reload the agreement and check which expiration date was saved.<br>2. If another date is still required, submit one update from the refreshed page. |
| `tenant-process` | `POST /tenants/:tenantId/mails` | A concurrent write has already committed the same tenant event-stream version; `eventRepository` throws `eventConflictError` from `TenantService.addTenantMail`. | **CAN HAPPEN** — two tenant admins can update the same contact email from separate sessions using the normal contact drawer. | **Data precondition:** tenant A has two admin sessions and an existing contact email; both sessions loaded the same contact state.<br>1. In both sessions, go to `/aderente/anagrafica` and choose _Modifica_ in _Contatti_.<br>2. Enter a different valid email in each drawer.<br>3. Choose _Aggiorna_ in both sessions before either request completes. | 🟢 **Easy resolution**<br>1. Reload the tenant page and check which contact email was saved.<br>2. If another address is still required, submit one update from the refreshed page. |
| `tenant-process` | `DELETE /tenants/:tenantId/mails/:mailId` | A concurrent write has already committed the same tenant event-stream version; `eventRepository` throws `eventConflictError` from `TenantService.deleteTenantMailById`. | Cannot happen — the frontend has no delete-mail service or control; `PartyContactsSection` opens `UpdatePartyMailDrawer`, which only issues the POST endpoint. | — | — |
| `tenant-process` | `POST /tenants/delegatedFeatures/update` | A concurrent write has already committed the same tenant event-stream version; `eventRepository` throws `eventConflictError` from `TenantService.updateTenantDelegatedFeatures`. | **CAN HAPPEN** — two tenant admins can change delegation availability from separate sessions while both hold the same tenant state. | **Data precondition:** tenant A has two admin sessions, the required delegation-eligibility attribute is active, and both sessions loaded the same availability values.<br>1. In both sessions, open `/aderente/deleghe` and select _Disponibilità_.<br>2. Choose _Modifica_ and change the same availability switch in both drawers.<br>3. Choose _Aggiorna_ in both sessions before either request completes. | 🟢 **Easy resolution**<br>1. Reload _Disponibilità_ and check which values were saved.<br>2. If another value is still required, submit one update from the refreshed page. |
| `tenant-process` | `POST /tenants/:tenantId/attributes/certified` | A concurrent write has already committed the same tenant event-stream version; `eventRepository` throws `eventConflictError` from `TenantService.addCertifiedAttribute`. | **CAN HAPPEN** — two certifier admins can assign an attribute to the same tenant from separate sessions before either assignment completes. | **Data precondition:** tenant C is a certifier, tenant A does not yet have a certified attribute owned by C, and two C admin sessions are open.<br>1. In both sessions, go to `/aderente/certificatore` and select _Assegnazione attributi_.<br>2. Choose _Assegna attributo_; select tenant A in _Ente assegnatario_ and the same item in _Nome dell'attributo_.<br>3. Choose _Assegna attributo_ in both drawers before either request completes. | 🟢 **Easy resolution**<br>1. Reload the assignment list and check whether the attribute is assigned to tenant A.<br>2. If it is still missing, submit one assignment from the refreshed page. |
| `tenant-process` | `POST /tenants/:tenantId/attributes/certifiedDiscrete` | A concurrent write has already committed the same tenant event-stream version; `eventRepository` throws `eventConflictError` from `TenantService.addCertifiedDiscreteAttribute`. | **CAN HAPPEN** — two certifier admins can assign the same certified discrete attribute to the same tenant from separate sessions before either assignment completes. | **Data precondition:** tenant C is a certifier, `FEATURE_FLAG_ATTRIBUTE_CERTIFIED_DISCRETE` is enabled, tenant A does not yet have the selected discrete attribute, and two C admin sessions are open.<br>1. In both sessions, go to `/aderente/certificatore` and select _Assegnazione attributi_.<br>2. Choose _Assegna attributo_; select tenant A, the same certified discrete attribute, and a valid _Valore numerico_.<br>3. Choose _Assegna attributo_ in both drawers before either request completes. | 🟢 **Easy resolution**<br>1. Reload the assignment list and check whether the discrete attribute is assigned to tenant A with the expected value.<br>2. If it is still missing, submit one assignment from the refreshed page. |
| `tenant-process` | `POST /tenants/attributes/declared` | A concurrent write has already committed the same tenant event-stream version; `eventRepository` throws `eventConflictError` from `TenantService.addDeclaredAttribute`. | **CAN HAPPEN** — two tenant admins can declare the same revoked attribute from separate sessions before either request completes. | **Data precondition:** tenant A has two admin sessions and the same declared attribute is revoked in A's registry.<br>1. In both sessions, go to `/aderente/anagrafica` and find that attribute under _Attributi_.<br>2. Choose _Dichiara attributo_ in both sessions before either request completes. | 🟢 **Easy resolution**<br>1. Reload the attributes section and check whether the attribute is declared.<br>2. If it remains revoked, choose _Dichiara attributo_ once from the refreshed page. |
| `tenant-process` | `POST /tenants/:tenantId/attributes/verified` | A concurrent write has already committed the same tenant event-stream version; `eventRepository` throws `eventConflictError` from `TenantService.verifyVerifiedAttribute`. | **CAN HAPPEN** — two provider admins can verify the same required attribute for an agreement from separate sessions before either verification completes. | **Data precondition:** tenant A is the provider of an active agreement with tenant B, and the agreement requires a verified attribute not yet verified by A; two A admin sessions are open.<br>1. In both sessions, open `/erogazione/richieste/{agreementId}`.<br>2. For the same attribute, choose _Verifica attributo_ and select _Senza scadenza_.<br>3. Choose _Verifica attributo_ in both drawers before either request completes. | 🟢 **Easy resolution**<br>1. Reload the agreement and check whether the attribute is verified.<br>2. If it remains unverified, verify it once from the refreshed page. |
| `tenant-process` | `DELETE /tenants/:tenantId/attributes/verified/:attributeId` | A concurrent write has already committed the same tenant event-stream version; `eventRepository` throws `eventConflictError` from `TenantService.revokeVerifiedAttribute`. | **CAN HAPPEN** — two provider admins can revoke the same verified attribute for an agreement from separate sessions before either revocation completes. | **Data precondition:** tenant A is the provider of an active agreement with tenant B, and the verified attribute is currently verified by A; two A admin sessions are open.<br>1. In both sessions, open `/erogazione/richieste/{agreementId}`.<br>2. For the same attribute, choose _Revoca attributo_.<br>3. Choose _Revoca attributo_ in both drawers before either request completes. | 🟢 **Easy resolution**<br>1. Reload the agreement and check whether the attribute is revoked.<br>2. If it is still verified, retry once from the refreshed page. |
| `tenant-process` | `DELETE /tenants/attributes/declared/:attributeId` | A concurrent write has already committed the same tenant event-stream version; `eventRepository` throws `eventConflictError` from `TenantService.revokeDeclaredAttribute`. | **CAN HAPPEN** — two tenant admins can revoke the same declared attribute from separate sessions before either revocation completes. | **Data precondition:** tenant A has two admin sessions and an active declared attribute in A's registry.<br>1. In both sessions, go to `/aderente/anagrafica` and find the declared attribute under _Attributi_.<br>2. Choose _Revoca attributo_ in both sessions before either request completes. | 🟢 **Easy resolution**<br>1. Reload the attributes section and check whether the attribute is revoked.<br>2. If it remains active, revoke it once from the refreshed page. |
