# Checked process endpoints

Repositories checked: `interop-be-monorepo` (99ad7fe7f) and `pdnd-interop-frontend` (7e34f23b).

Note: the BFF routes for `DELETE /agreements/{agreementId}`, `POST /agreements/{agreementId}/update` and `POST /agreements/{agreementId}/upgrade` use `emptyErrorMapper`, so the BFF raises no errors of its own for them. Their non-500 errors are the process errors, which reach the FE with their process status because the BFF forwards `Problem` responses (`problemErrorsPassthrough`).

Note: the BFF routes `DELETE /inAppNotifications`, `POST /inAppNotifications/bulk/markAsRead` and `POST /inAppNotifications/bulk/markAsUnread` (`inAppNotificationRouter`) use `emptyErrorMapper`, and so do the in-app-notification-manager routes they forward to (`DELETE /notifications`, `POST /notifications/bulk/markAsRead`, `POST /notifications/bulk/markAsUnread` in `packages/in-app-notification-manager/src/routers/notificationRouter.ts`). The manager services `deleteNotifications`, `markNotificationsAsRead` and `markNotificationsAsUnread` never throw, so no service-specific error can occur. The only non-500 statuses come from common codes mapped by `defaultCommonErrorMapper`, and none is reachable from the FE:

- `operationForbidden` → 403: the manager's `validateAuthorization` accepts only `admin`, `api`, `security` and `reviewer`. Cannot happen: the FE route `/notifiche` (`NOTIFICATIONS` in `src/router/routes.tsx`) has the same `authLevels`.
- `badRequestError` → 400: raised by the body validation (`ids` must be UUIDs). Cannot happen: the bulk buttons in `NotificationsTable.tsx` render only when at least one row is selected, and the ids come from rendered notifications, which the API returns as UUIDs.
- `contentTooLargeError` → 413: Cannot happen: the ids are limited to the rendered page.
- `tooManyRequestsError` → 429: Cannot happen: a single user action sends a single request, well below the rate limiter budget.
- `tokenVerificationFailed` → 401: Cannot happen under normal use with a valid session.
